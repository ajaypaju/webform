## 1. Measured results: what the rows mean

For the table these rows explain, see [ARCHITECTURE.md §2](ARCHITECTURE.md#measured-results-local-dev--not-a-benchmark).

- **Within limits** is the clean number: 200/s sustained for two minutes, every request acked on the first attempt, p99 21 ms end to end (validation, produce, flush, delivery report), generator queueing p99 2 ms.
- **Default spike** is the product refusing by design: the per-form bucket at the time admitted 2,000 then 200/s, so a 2,000/s spike on one form was 532,326 × 429 responses and 58,476 ids that gave up after 6 attempts. The defaults were raised afterwards to 5,000 / 2,000/s (`config/ingest.php`: an abuse ceiling, not a traffic shaper) and this run was not repeated. The ack latency there is retry time, not server time. The generator itself saturated (2,048 workers held in retry sleeps; queueing p50 120 s) and says so in its report — the achieved rate is the limiter's, not the laptop's.
- **Chaos** is the claim under fault: 0 acked ids missing across a consumer stop, a Postgres stop, a Redpanda stop and a process crash. The 1,689 "refused but stored" ids are the ambiguous-ack case from §4 — the client saw a 503 or a network error after the broker had in fact persisted the record — stored exactly once because ids are reused and `submission_ids` dedupes. Recovery after the crash took ≈ 45 s before the restarted consumer got its partitions back: Kafka's `session.timeout.ms` for the dead member, not a design property of this system.
- **Drain**: neither the consumer nor PostgreSQL came near saturation (each 500-row batch commits in 11–23 ms); the 2.5 s includes consumer start-up. What *did* saturate during the spike and chaos runs was the load generator, and what bound the acked rate was the per-form bucket — both reported by the tooling rather than hidden.

## 3. Requirement evidence

### 3.1 Bursty load

Summary and measured result: [ARCHITECTURE.md §5.1](ARCHITECTURE.md#51-bursty-load).

A per-worker circuit breaker ([app/Ingest/SubmissionProducer.php](app/Ingest/SubmissionProducer.php)) opens after N consecutive delivery failures and answers 503 without a broker round-trip for a cooldown, then lets one request probe — otherwise a burst during a broker outage pins every worker on `message.timeout.ms`. A fatal librdkafka error recreates the producer; an idempotent producer stays broken otherwise.
Evidence: [tests/Feature/Kafka/ProducerTest.php](tests/Feature/Kafka/ProducerTest.php); breaker open/probe/close, re-open on a failed probe, fatal recreate, and the HTTP path returning 503 never 202 while the broker is down — [tests/Feature/Ingest/SubmissionProducerTest.php](tests/Feature/Ingest/SubmissionProducerTest.php), [SubmissionsTest.php](tests/Feature/Ingest/SubmissionsTest.php).

### 3.2 No lost submissions

Summary and reconciliation result: [ARCHITECTURE.md §5.2](ARCHITECTURE.md#52-no-lost-submissions).

Spam (honeypot, bad or too-fresh or expired render token) receives a decoy 202 with a fresh id and is never produced (I13). ### 3.3 Tenant isolation

Summary, the three layers and the role table: [ARCHITECTURE.md §5.3](ARCHITECTURE.md#53-tenant-isolation). The dashboard side of this requirement is §4 below.

RLS is deliberately not `FORCED`. `FORCE` binds only the table owner; with the owner running migrations and tests it would need a `USING (true)` policy, and `FORCE` plus an allow-all policy restricts nothing while suggesting it does. The owner is kept out of the runtime by credentials instead, and [app/Database/RuntimeRole.php](app/Database/RuntimeRole.php) verifies them: the connection's `current_user` must be the role expected for `APP_ROLE`, and must not be superuser, `BYPASSRLS`, or the owner of any table in `public`. `api` and the consumer check at boot and refuse to start; `ingest` checks on `ConnectionEstablished` — dispatched inside `DatabaseManager::connection()` before the connection is returned, so the first query cannot run unchecked — because the data plane must start while PostgreSQL is down (I12). A failed check purges the connection (otherwise the worker would keep an unchecked one) and writes the reason to the process's stderr.

The control plane's `AuthenticateApiKey` middleware hashes the bearer token, resolves it with `resolve_api_key`, binds `TenantContext` with `app()->scoped()`, and runs the rest of the request inside one transaction that starts with `set_config`; route-model binding is ordered after it so lookups already see the tenant. A 401 has one body for missing and wrong keys. Eloquent models carry a `TenantScope` that throws when no context is bound (fail closed at the app layer too). Streamed responses outlive that transaction and must open their own (CLAUDE.md I11).

Evidence: [tests/Feature/Schema/ApiRoleTest.php](tests/Feature/Schema/ApiRoleTest.php), [IngestRoleTest.php](tests/Feature/Schema/IngestRoleTest.php), [WriterRoleTest.php](tests/Feature/Schema/WriterRoleTest.php), [RuntimeRoleTest.php](tests/Feature/Schema/RuntimeRoleTest.php) (each role on its own connection against real PostgreSQL); middleware, scoped rebinding across consecutive requests with different keys, fail-closed outside the transaction, and 404 for another tenant's form on every endpoint — [tests/Feature/Api/AuthTest.php](tests/Feature/Api/AuthTest.php), [FormsTest.php](tests/Feature/Api/FormsTest.php), run with the api role as the request connection. ## 4. Dashboard authentication

The three-sentence version and the isolation mechanism it rides on are in [ARCHITECTURE.md §5.3](ARCHITECTURE.md#53-tenant-isolation).

### 4.1 Sessions: two ways in, one tenant path

**Dashboard sessions: two ways in, one tenant path.** The dashboard (`/login`, `/signup`, `/dashboard/...`, served by the `api` role only) is a second way into the same tenant context, not a second identity model. A session is started either by email + password (a `users` row, bcrypt via Laravel's default hasher, owner of a tenant through `tenant_users`) or by pasting an API key (operator-provisioned tenants have no user; the key is hashed and resolved by the same `resolve_api_key`). Either way the session holds ids only — `tenant_id`, and `user_id` for a password login — never the key or the password, in a server-side Redis session on `api` (`ingest` keeps `SESSION_DRIVER=array` and sets no cookie). Both paths then funnel into the same middleware and the same `TenantTransaction` as a bearer request does. The cookie is `httpOnly`, `SameSite=Lax`, `Secure` outside `APP_ENV=local`; the session id is regenerated on login and the session destroyed on logout; login attempts are rate-limited per IP. [app/Http/Middleware/DashboardTenant.php](app/Http/Middleware/DashboardTenant.php) reads `tenant_id` from the session and hands it to the same [app/Tenancy/TenantTransaction.php](app/Tenancy/TenantTransaction.php) helper `AuthenticateApiKey` uses — scoped `TenantContext`, one transaction, `set_config` first — so every query behind it is the same fail-closed path with the same RLS policy. For a password session it then re-reads the `tenant_users` row inside that transaction on every request: a removed member loses the dashboard on their next request, not at their next login. Membership is tenant data — `tenant_users` has the same policy as `forms`, so a tenant's member list is visible only inside that tenant; the one question login must ask before any tenant is set ("which tenants does this user belong to?") goes through `resolve_user_tenants`, a definer function like `resolve_api_key`. `users` has no RLS: a user is not tenant data and may belong to several tenants later. Why the key stays out of the browser: a key is a long-lived bearer credential with no expiry, revocation is by deleting the row, and anything readable by page JavaScript is readable by an XSS; a session is revocable server-side, expires, and its cookie is unreadable to scripts. The two surfaces never cross: `/v1` runs without `StartSession` or CSRF, so a session cookie is simply not read there and a bearer key is the only credential; the dashboard runs under the `web` group and `DashboardTenant` ignores `Authorization`, so an API key alone gets a redirect to `/login` (JSON 401 with `Accept: application/json`). Every mutating dashboard route requires a CSRF token; the builder sends it as `X-CSRF-TOKEN` from the page's JSON data block, and Laravel's JS-readable `XSRF-TOKEN` cookie is switched off ([app/Http/Middleware/PreventRequestForgery.php](app/Http/Middleware/PreventRequestForgery.php)) so the only cookie the browser holds is the `httpOnly` session. Timestamps in the dashboard are shown in UTC and labelled so; the date filters are read as UTC too. Publishing and draft validation from the dashboard go through [app/Forms/FormEditor.php](app/Forms/FormEditor.php), the same class `FormController` uses, so the two entry points cannot disagree on what a valid or a compatible definition is.

### 4.2 Signup and verification

**Signup and verification.** `POST /signup` ([app/Accounts/Signup.php](app/Accounts/Signup.php)) creates the user, the tenant, the owner membership and the first API key in one transaction — run through `TenantTransaction` for the tenant it is about to create, so the api role's own `WITH CHECK` policies admit exactly those rows — and logs the new user in; any failure rolls all four back. The response is the same page for a new and an existing address (`/signup/done`, rendered without session chrome), so the form cannot be used to enumerate accounts; an existing owner is told by email instead. Password rule: minimum 12 characters, bcrypt. Laravel's `Password::uncompromised()` was not used: it calls haveibeenpwned over HTTP on every signup, and neither HTTP role may depend on an external service. Email verification is a signed, expiring URL (`URL::temporarySignedRoute`, checked by the `signed` middleware); there is no mail transport in this build, so the link — and the "someone signed up with your address" notice — are written to the api log (`docker compose logs api`), and the screen says so. Sending mail is designed, not built (§11). An unverified user can log in and build, but not publish or create keys; verification lifts both gates. Per-IP limits cover signup, login (password, key and verification links share one bucket) and verification resends.

### 4.3 API keys and their lifecycle

`api_keys.key_hash` is readable by no app role; `resolve_api_key(key_hash)` is `SECURITY DEFINER` with a pinned `search_path`, executable by `webform_api` only, ignores revoked keys, and records `last_used_at` (at most once a minute per key — it is the only code that sees the hash, and the control plane is not a hot path). The api role sees the other `api_keys` columns of its own tenant so the dashboard can list, create and revoke keys. Cross-tenant ids return 404.
**API key lifecycle.** The dashboard lists a tenant's keys by prefix with `created_at` and `last_used_at`, creates a key (plaintext shown once, in the response that created it), and revokes one; `resolve_api_key` ignores revoked keys, so a revoked key gets 401 on the next `/v1` request. A tenant always keeps at least one live key: the last one cannot be revoked (the live keys are locked `FOR UPDATE` so two concurrent revokes cannot both pass the count). `make tenant` (`tenants:create`, run as the owner role) still provisions a tenant with a key and no user.
A session started by pasting a key also records that key's id (`resolve_api_key_id`, a definer function like the other two) and `DashboardTenant` re-checks `revoked_at` on every request, so revoking a key ends the dashboard session it started on that session's next request — the same per-request pattern as the membership check.

## 5. Validation design: detail

The summary paragraph and the parity proof are in [ARCHITECTURE.md §7](ARCHITECTURE.md#7-validation-design).

**Why not Laravel's Validator.** It is loosely typed by design: `integer` accepts `"42"`, `date` uses `strtotime`, `email` is RFC-ish, `.`/`*` in a rule key means nesting — each a place where browser and server would disagree. The validator is pure PHP: `Normalizer` (JS `trim` set, code-point lengths, safe-integer float folding), `Visibility` (backward-only conditions, hidden values dropped before rules), `FieldChecks` (strict JSON types, one method per type), `SafePattern`, and `DefinitionRules` at save time.
**Regex safety.** PHP has no RE2, so backtracking is contained, not avoided: `SafePattern` wraps the pattern in a control-character delimiter (no escaping, meaning preserved), adds `Du`, lowers `pcre.backtrack_limit`/`pcre.recursion_limit` around the call (restored in `finally`), caps pattern and subject length, and maps `preg_match === false` to the `pattern` code, never an exception. `DefinitionRules` admits only the subset PCRE and JS (`u`) read identically: no backreferences, lookaround, atomic/possessive constructs, inline flags, PCRE-only escapes, POSIX classes, octal or lenient `{ } ]`; `\p{..}` limited to short General_Category names. `tests/js/patterns.test.mjs` compiles every accepted pattern with `new RegExp(p, 'u')`.
**Known semantic gaps** (`conformance/README.md`, documented, not fixed): JS `\s` includes Unicode spaces, PCRE without UCP is ASCII-only; `.` excludes `\r`, U+2028, U+2029 in JS but not PCRE; and JS has no backtrack limit (V8's linear fallback engine cannot be used because it does not support the `u` flag), so a catastrophic pattern would run for seconds in the browser. `render.js` therefore evaluates patterns in a Web Worker with a 50 ms budget and skips the client-side check on timeout — the field submits and the server decides; the parity suite skips the `redos_*` case for the same reason, server-side protection being proven by the PHP test. The server is authoritative, so the effect of the remaining gaps is client/server disagreement on exotic input, never bad stored data.
